# ADR-0023: Suspend and resume V2 commands through durable reactions

- Status: Implemented for trusted local V2 kernels and gated loopback HTTP/developer-panel integration; production lifecycle deferred
- Date: 2026-10-18

## Context and current transaction map

The extension kernel owns command execution. `executeCommand` opens `BEGIN IMMEDIATE`, authenticates the principal, reads the exact campaign lock and entity revisions, authorizes command intent, resolves host-supplied randomness, validates semantic effects, applies them with `effects.applyInTransaction`, and commits extension events and the idempotent command receipt. It rejects nested transactions.

The reaction kernel persists windows, choices, terminal events and effects in SQLite. Its standalone `open`, `submit`, `expire` and `adjudicate` operations own a `BEGIN IMMEDIATE` transaction and reject nesting. The host adapter can alternatively call `openInTransaction`, `submitInTransaction`, `expireInTransaction` and `adjudicateInTransaction` only while it already owns an active SQLite transaction. Those methods share the same validation/decision implementation and never begin, commit or roll back. An exception leaves the outer transaction open so its owner chooses the rollback/commit boundary. Completion and the trusted host effect adapter execute within that existing boundary. Completion/effect callbacks receive domain data only; no raw database connection or transaction callback is passed to module resolvers or effect handlers.

The transaction-aware reaction seam allows an extension-owned coordinator to compose suspension and terminal resumption inside one `BEGIN IMMEDIATE`, without a nested transaction. The extension kernel constructs one reaction kernel over the same `DatabaseSync` connection. Module resolvers receive only immutable JSON inputs; effect handlers receive only immutable entity/effect snapshots. Host configuration callbacks resolve responder identities and reauthorize the original actor, but no database handle or transaction callback is passed to a module.

## Implemented continuation lifecycle

1. The authenticated command starts in the extension kernel's `BEGIN IMMEDIATE` and is validated against current membership/grants, entity revisions, command descriptor and exact lock as today.
2. A trusted resolver may return a bounded serializable continuation plus `reaction` intent: ordering, visibility, named audience policies (`command-actor`, `entity-owner`, or `campaign-gm`), action schemas and priorities. The host resolves those policies to currently authorized principals; module output does not name participants or authenticated identities. A reaction continuation requires an exact resolver registration with a typed `resume` implementation. Suspended outputs cannot include effects and workflow transitions cannot currently suspend.
3. In the command transaction, the host stores the original sanitized request and its canonical hash, command/resolver identity, exact lock, actor principal, expected revisions, continuation, suspension transcript, and pending receipt. It opens the durable reaction window with `openInTransaction`; the window, parent row, event and receipt commit together. No suspended gameplay effects run.
4. Host-only `submitReaction`, `expireReaction`, and `adjudicateReaction` entry points own one immediate transaction and invoke the existing reaction kernel's transaction-aware methods. Current responder authorization is checked by the host callback. The kernel preserves exact operation retries, changed-payload conflict, single decision per responder and deterministic ordered/simultaneous decisions.
5. On terminal reaction status, the kernel's trusted completion callback checks pending/window/continuation identities, reauthorizes the original actor, reloads source/targets, checks expected revisions, target visibility and exact current lock, then calls the exact pinned resolver's `resume` with the typed continuation, terminal status and ordered decisions. Resume randomness is freshly host supplied. Resumed effects go through `effects.applyInTransaction`.
6. Reaction choice, resumed effects/effect receipt, parent completion or safe terminal conflict receipt, parent/reaction events, and terminal window status are in the same SQLite transaction. Any unexpected exception rolls all of it back. Stale source/target revision, changed lock or revoked original actor becomes a persisted `conflicted` parent receipt with no resumed effects. Exact parent retries return pending/completed/conflicted receipt without resolving or drawing again; changed payload conflicts.

## Failure and concurrency policy

The only commit boundaries are suspension and terminal completion. An exception at any point before either commit rolls back all writes made in that transaction, including choices, effects, parent/reaction receipts, window transitions and audit events. SQLite's `BEGIN IMMEDIATE` serializes competing submissions on the single host; the losing decision observes the committed choice/window status and cannot apply effects again. Expiry uses host time and enters the same completion path as decline. Simultaneous policy waits for all eligible responders; priority policy follows the existing deterministic priority/submission order. Disconnect/restart leaves a pending row that can be projected and resumed after current authority is checked.

Continuation data is bounded JSON stored in host tables and excluded from reaction HTTP projections. Reaction actions and declarations are module-owned, audience-to-principal mapping and current authorization are host-owned. The gated loopback API exposes authenticated list/detail, accept/decline, expiry and GM adjudication operations; campaign and principal are derived from host context, and exact capability-lock headers are checked. The developer panel uses real HTTP and renders only authorized entity, reaction and event projections. Initial and resumed transcripts bind host-supplied random values, and public events include only public draws/outcomes/choices. This is local SQLite protection/projection, not encryption at rest.

## Consequences and limits

This design composes the existing resolver, reaction and effect kernels; it does not add another rules/execution kernel. The host coordinates lifecycle and transaction ownership while rules, eligibility, interpretation, and proposed effects stay module-owned. The first implementation remains gated, loopback-only and limited to trusted bundled modules. This does not close #145's production identity, multi-process, power-loss, archive/restore or publisher-provenance gates, and it does not add offline V2 support.

The transaction-aware reaction seam and typed pending-command suspend/resume lifecycle are implemented for trusted local kernels. A deliberately rules-neutral bundled interruption example is reachable through the authenticated, default-off loopback V2 API and developer panel. Real-browser evidence covers isolated GM, initiator and responder contexts, restart while pending, response after restart, and exactly-once resumed effect. This does not implement Revised 5e reactions or make them playable. Pending commands are not included in the V2 extension snapshot or existing archive/backup formats; restore/export migration is deferred. Workflow command suspension is unsupported. No production multi-process, power-loss, production identity, publisher provenance or offline guarantees are claimed.

## Evidence from the transaction seam

The contracts now define bounded reaction audience intent and typed `ResolverResumeInput`; `executeResolver` binds continuation and ordered reaction decisions into the resumed transcript digest. `v2-extensions` stores pending commands and receipts, resumes only the exact registered resolver under the original lock, and composes through the existing reaction and semantic effect kernels. Regression tests cover restart before/after completion, accept/decline/expiry, original actor and responder revocation, stale lock/revision, altered retry payload, host randomness persistence, and injected rollback at pending-window, pending-receipt, reaction-submission, resume, effect and final-receipt boundaries. A contrasting narrative-interruption fixture exercises the same host lifecycle.

In addition, host integration tests cover authenticated route authority, identity spoof rejection, exact and changed retries, concurrent exact submissions, private continuation/outcome isolation, and visibility-filtered randomness for immediate and resumed commands. `scripts/v2-reaction-browser-acceptance.mjs` exercises the real gated host in three isolated browser contexts and restarts the host while a reaction remains pending. This demonstrates the generic protocol only: #138's Revised 5e encounter criteria and compatible backup/restore are still outstanding. #145 production host lifecycle gates remain outstanding.
